# Organic Agent-Owned Tools Merge Readiness Plan

_Status: implemented on this branch. W0-W7 are complete as of the final
verification sweep below._

## Readiness Standard

This branch is merge-ready only when the implemented behavior satisfies both:

- the v1 authority lifecycle from
  [agent-proposed-tools-governor-authority-implementation-plan.md](agent-proposed-tools-governor-authority-implementation-plan.md)
- the remaining organic external-tool requirements from
  [organic-agent-owned-tools-proposal.md](organic-agent-owned-tools-proposal.md)

Passing package tests is necessary but not sufficient. The merge gate is the
implemented lifecycle:

1. proposal
2. ratification
3. install execution
4. import audit
5. probe
6. verification
7. registration
8. exposure
9. invocation-time authorization
10. execution through bounded runtime
11. status/audit visibility
12. drift detection and repair-oriented staleing

## Must-Fix Workstreams

### W0 - Scope and Config Hygiene

Goal: remove avoidable merge-review ambiguity before deeper implementation.

Tasks:

- Decide whether the GPT-5.5/OpenAI provider migration remains in this branch or
  is split into a separate branch/PR.
- If kept, ensure commits and docs identify it as intentional branch scope.
- Fix `config.example.toml` so `providers.selection = "auto"` does not pair with
  an explicit empty `fallback_chain` that disables the intended OpenAI ->

- Add or adjust a config test proving copied example semantics match live
  intended provider selection.

Merge gate:

- `go test ./config ./provider`
- `git diff --check`

### W1 - Sandbox All External Command Paths

Goal: make external tool invocation, install, and probe use the same sandbox
execution boundary as normal `exec`.

Current risk:

- `tool/external_executor.go` invokes external tools with direct
  `exec.CommandContext("bash", "-lc", ...)`.
- `tool/tool_authority.go` runs install/probe commands with direct
  `exec.CommandContext(command[0], command[1:]...)`.
- These paths bypass `sandbox.Runner`, so manifest constraints and principal
  sandboxing are weaker than the rest of the tool runtime.

Tasks:

- Route process/subprocess external invocation through `sandbox.Runner.Run`.
- Route manifest install and probe commands through `sandbox.Runner.Run`.
- Preserve input-over-stdin and JSON output validation for invocation.
- Enforce timeouts and max output consistently.
- Reject unsupported filesystem/network constraints before execution.
- Add regression tests that fail if external commands can write outside the
  resolved sandbox scope.

Merge gate:

- `go test ./tool`
- Manual negative check: an external process tool cannot read or write host paths
  hidden from the principal sandbox.

### W2 - Runtime-Authored Verification Evidence

Goal: make verification depend on evidence generated by runtime audit/probe
commands, not on user-supplied status fields.

Current risk:

- `install_set` can accept `probe_status` and `probe_output`, then create a
  probe record. That lets the same manual transition self-author the evidence
  needed for verification.

Tasks:

- Stop `install_set` from creating probe records.
- Require `probe_run` to be the only path that writes passed/failed probe
  evidence.
- Require `audit_run` to be the only path that writes import audit evidence.
- Require verified installs to reference current runtime-authored passed probe
  and audit records.
- Preserve manual `pending`, `installed`, `failed`, and `stale` install states
  where they remain operationally useful.
- Update tests that currently verify by passing inline `probe_status`.

Merge gate:

- `go test ./tool ./session`
- Negative tests prove inline `probe_status` cannot verify an install.

### W3 - Real Audit Baselines, Fingerprints, and Drift Staleing

Goal: make audit compare current executable reality against the baseline that was
verified.

Tasks:

- Define a deterministic fingerprint over the manifest fields that affect
  authority and execution:
  - tool name
  - owner
  - version
  - execution mode
  - execution entry
  - workdir
  - input/output schemas
  - constraints
  - install command
  - probe command
- Include a filesystem fingerprint for local process/subprocess entry files.
- Store audit baseline fingerprint(s) in durable audit/install records.
- On `install_show`, `audit_show`, registration, exposure, and invocation,
  compare the current fingerprint to the verified baseline.
- Mark install/audit state stale with a concrete reason when drift is detected.
- Block registration and invocation for stale external tools.
- Surface stale reasons in lifecycle list/show output and `/status` projection.

Merge gate:

- `go test ./tool ./runtime ./session`
- Tests mutate a manifest/entry after verification and prove staleing blocks
  registration/invocation with an operator-readable reason.

### W4 - Execution-Mode Semantics

Goal: make each accepted manifest execution mode have honest lifecycle behavior.

Tasks:

- Define process/subprocess as executable through the sandbox runner.
- Define container mode lifecycle separately from process mode.
- Define workspace_runner mode lifecycle separately from process mode.
- For modes not yet implemented as executable, keep them importable and
  diagnosable but not verifiable/registerable as executable capability.
- Ensure status explains why a manifest is present but not executable.
- Do not let a non-executable mode proceed through verified -> registered ->
  exposed -> invoked as if it were process-backed.

Merge gate:

- `go test ./tool ./runtime`
- Tests prove container/workspace_runner cannot be falsely verified by the
  process executor.

### W5 - End-to-End Lifecycle Flow

Goal: prove the whole authority chain works as one flow, not only as isolated
commands.

Tasks:

- Add an integration-style test fixture for a repo-local external process tool.
- Cover successful lifecycle:
  1. submit proposal
  2. ratify proposal
  3. create pending install record
  4. run install command
  5. run audit
  6. run probe
  7. mark verified
  8. register from external manifest
  9. expose to a target principal
  10. invoke successfully
- Cover negative lifecycle paths:
  - rejected proposal blocks registration
  - installed but unaudited blocks verification
  - audited but unprobed blocks verification
  - verified but unregistered blocks invocation
  - registered but unexposed blocks invocation
  - revoked exposure blocks invocation
  - drift after verification blocks registration/invocation

Merge gate:

- `go test ./tool ./decision ./runtime ./session`
- Manual lifecycle run documented in the PR notes.

### W6 - First External-Tool Pilot

- Validate one narrow read-only workflow.

Merge gate:

- Manual pilot steps are reproducible on a prepared host.
- No browser/domain special casing is added to Aphelion core.

## Sequential Dependencies

These workstreams are on the critical path and should be integrated in order:

1. W0 - Scope and config hygiene.
2. W1 - Sandbox all external command paths.
3. W2 - Runtime-authored verification evidence.
4. W3 - Real audit baselines, fingerprints, and drift staleing.
5. W5 - End-to-end lifecycle flow.
6. W6 - First external-tool pilot.
7. W7 - Final docs/status/verification.

Reasoning:

- W1 must land before W2/W3 can make strong claims about trustworthy probe and
  audit evidence.
- W2 must land before W3 can define a meaningful verified baseline.
- W3 must land before W5 can assert drift-aware end-to-end behavior.
- W5 should land before W6 so the pilot exercises a proven generic lifecycle.
- W7 must be final because docs and status should describe implemented behavior,
  not intended behavior.

## Parallel Agent Execution Plan

Use parallel agents for bounded, disjoint work only. Avoid parallel edits to the
same files unless the integration owner explicitly sequences patches.

### Can Run In Parallel Immediately

A. Config/docs hygiene scout

- Owns: `config.example.toml`, `requirements/config.md`, config tests if needed.
- Output: patch for W0 config/example consistency.
- Can run while W1 implementation starts because it touches mostly config files.

B. Execution-mode semantics design/test scout

- Owns: new tests around container/workspace_runner behavior and a short design
  note in the merge-readiness doc or requirements.
- Output: failing tests or proposed invariants for W4.
- Should avoid editing `tool/external_executor.go` while W1 is active.

C. End-to-end fixture design scout

- Owns: test fixture shape and proposed test cases for W5.
- Output: fixture scripts/manifests and a draft test skeleton if it can avoid
  touching W1/W2 internals.
- Should not finalize assertions that depend on W2/W3 until those APIs settle.

D. Documentation/status inventory scout

- Owns: identifying exact docs/status text that will need updates.
- Output: checklist only until W3/W5 behavior lands.
- Should not preemptively mark remaining items implemented.

### Can Run In Parallel After W1 Lands

E. Verification-evidence worker

- Owns: W2 changes in `tool/tool_authority.go`, session record usage, and tests.
- Depends on W1 because probe/audit evidence should come from sandboxed runtime
  commands.

F. Execution-mode worker

- Owns: W4 behavior and tests for process/container/workspace_runner semantics.
- Can run alongside W2 if write scopes are kept separate and both coordinate on
  shared manifest/status language.

### Can Run In Parallel After W2 Lands

G. Drift fingerprint worker

- Owns: W3 fingerprint computation, durable record fields, stale checks, and
  tool/session tests.
- Depends on W2 so fingerprints attach to runtime-authored evidence.

H. Status projection worker

- Owns: `/status` rendering and requirements text for stale reasons.
- Can run alongside W3 only after fingerprint/stale status fields are defined.

### Should Stay Sequential

- Integrating W1 into the executor and install/probe paths.
- Integrating W2 verification rules after W1.
- Integrating W3 durable schema/fingerprint behavior after W2.
- Final W5 end-to-end lifecycle assertions after W1-W4 behavior is stable.
- W6 pilot validation after W5 proves the generic lifecycle.
- W7 final docs and verification after behavior is implemented.

## Integration Owner Rules

- Keep one owner responsible for `tool/tool_authority.go` during W1-W3.
- Do not let two workers edit durable session schema/migrations concurrently.
